Security

Aurum holds money information, so it is built to be private by default, and the protections are tested.

What it protects, and from whom

Assets: balances, holdings, card and bank transactions, payslips, API keys, e-mail and PDF passwords. Threats considered: another site in your browser attacking the local server; someone on your network or the internet probing it; a copied database or backup; a lost phone; malicious text in a web page, merchant name or e-mail trying to steer the assistant.

What is in place

AreaProtection
NetworkListens on 127.0.0.1 only (waitress). Requests must carry a known Host header, which defeats DNS rebinding. The phone path is a private Tailscale HTTPS address, never the public internet.
Sign-inEvery route requires a session except a short allow-list (sign-in pages, static files). Passwords: 12+ characters, scrypt (N=215), constant-time compare, growing lockout after three failures. No default password exists; first run is a setup page.
Face IDWebAuthn passkeys verified server-side: challenge, origin, app identity, user-verification flag, signature and sign counter. Phones never accept passwords. Remote sessions lock after 2 idle minutes.
SessionsRandom 256-bit cookie, only its hash is stored. HttpOnly, SameSite=Strict, Secure over HTTPS. Listed, revocable, expiring.
CSRFEvery state-changing request needs a custom header, a same-origin Sec-Fetch-Site, and an allowed Origin.
BrowserStrict CSP (script-src 'self', no framing, no external requests), nosniff, no-referrer, Permissions-Policy, COOP/CORP, HSTS on HTTPS, no-store on API pages. Fonts, charts and QR codes are vendored: no third-party requests from the page.
Secrets at restAPI keys, broker tokens, mail and PDF passwords are sealed before they touch the database: Windows DPAPI on Windows (no key file), Fernet with an owner-only key file elsewhere. They are never returned to the browser, and the settings API exposes only a short allow-list.
SSRFWeb research resolves a host once, refuses private, loopback and link-local addresses, pins the connection to the checked address and re-checks every redirect.
AssistantNo trading tool. It can only read and propose; every change is a card you approve. Text from the web, merchants and e-mail is treated as data, never instructions. Errors shown to you are generic; details stay in the log.
Demo modeA separate database file with invented data. In a demo session, anything that touches a real account, mailbox, broker or phone is blocked.
BackupsContain no password hash, sessions, passkeys or keys (tested).
Repository.env, data/, *.db, keys and credentials are git-ignored. backend/test_repo_clean.py fails the build on key-shaped strings, private keys or personal e-mail addresses, and CI runs it on every push.

Run the checks yourself: python backend/test_security.py exercises setup mode, lockout, forged and cross-site requests, rebinding hosts, the remote rules, a full Face ID flow with a software authenticator, idle locking, sealed secrets and clean backups.

Your responsibilities

  • Disk encryption (BitLocker, FileVault, LUKS). The database is a normal SQLite file apart from the sealed secrets.
  • Back up data/; on macOS/Linux keep data/secrets.key out of any backup that also holds the database, or the encryption is moot.
  • Never expose the port to the internet, and do not use tailscale funnel.
  • Choose a long password and a phone passcode. An unlocked, signed-in computer is a signed-in app.
  • Third parties you opt into see what you send them: Yahoo Finance (tickers), your AI provider (the question and the data needed for it), Gmail (read-only IMAP), your broker (read-only).
  • Dependencies are pinned in requirements.txt; update deliberately and re-run the tests.

Reporting a problem

Please report vulnerabilities privately through GitHub's private vulnerability reporting rather than a public issue. See SECURITY.md.
